# Custom enchantment system — design

Status: **design, nothing built yet.** Everything technical below was verified
against the decompiled 1.7.10 source and a live audit of the actual pack, not
assumed.

## What the audit found

`config/qfcontent-enchantments.txt`, generated by `EnchantmentAudit` on a real
pack launch:

- **67 of 256** enchantment ID slots are in use. 189 free.
- Largest free blocks: **132–189 (58 slots)** and **214–254 (41 slots)**.
- Proposal: reserve **132–189** for this mod. Far more than we need, contiguous,
  and clear of every mod currently installed.

### The pack already has these — do not rebuild them

This is the single most important result. Several obvious "custom enchant" ideas
already exist here:

| Last Stand | OpenBlocks | Survive-a-fatal-hit |
| Multiply | TragicMC | Multishot / volley |

| Soul Stealer | SoulShards | Soul/essence harvesting |
| Decay, Slay, Absolve, Rune Break | TragicMC | Flat "bonus damage vs type" |

## Architecture

Three decisions, each with the evidence behind it.

### 1. Register real `Enchantment` objects, not pure NBT

With 189 free IDs there is no pressure to avoid the registry, and registering
properly gives us native tooltips, the enchant glint, persistence through
save/load, and `EnchantmentHelper.getEnchantmentLevel()` inside our event
handlers — all for free. Kept out of normal play by:

- `canApplyAtEnchantingTable()` → `false` — never rolls at an enchanting table
- `isAllowedOnBooks()` → `false` — never appears in vanilla loot books

so they exist only through our own books.

### 2. One shared base class solves the modded-item requirement

`Enchantment.canApply(ItemStack)` is just
`return this.type.canEnchantItem(stack.getItem());` — verified in the decompiled
source. Overriding it is the entire mechanism for supporting modded gear:

```java
public boolean canApply(ItemStack stack) {
    Item item = stack.getItem();
    if (item instanceof ItemSword || item instanceof ItemTool
            || item instanceof ItemArmor || item instanceof ItemBow) return true;
    return ConfigWhitelist.allows(category, item);   // for gear that extends none of them
}
```

Most modded weapons/tools/armor extend the vanilla classes, so they work
automatically. The config whitelist (by registry name) covers the ones that
don't — Battlegear, ICBM and MCHeli gear are the likely offenders.

### 3. Drag-and-drop needs an ASM coremod hook

Verified: Forge 1.7.10 has **no** slot-click or mouse-input event.
`GuiScreenEvent` exposes only init, draw and button-press. So there is no
event-based way to detect "player dropped item A onto item B".

The hook point is `Container.slotClick(int slotId, int clickedButton, int mode,
EntityPlayer player)` — public, server-authoritative, and called for every
inventory click in every GUI. An ASM transformer injecting at its head can
intercept "cursor holds our book, clicked slot holds a valid target", run the
roll, and cancel the vanilla swap.

**This is a real cost.** It means the enchant system spans two artifacts: this
mod plus a coremod transformer. The pack already ships `QuestForgeTweaks` doing
exactly this kind of ASM, so the pattern is established and proven here — but it
is meaningfully harder than the alternative.

**The alternative, for comparison:** `AnvilUpdateEvent` exists and is fully
usable (`left`, `right`, `output`, `cost`, `materialCost`, cancelable). Books
applied in an anvil would need no ASM at all and would take roughly a day less to
build. It loses the drag-and-drop feel.

## The book, and the roll

Our own item, not vanilla's enchanted book. NBT per stack:

```
QFBook: {
  ench: "executioner",   // which enchantment
  lvl: 2,                // level it grants
  success: 65,           // % chance to apply
  destroy: 20,           // % chance to destroy the item if it fails
  rarity: 3              // drives the name colour and the tooltip
}
```

Success and destroy are **rolled into the book when it is generated**, from a
range set by the loot table it came from. So two Executioner books are not
interchangeable — a 78%/10% book is a genuinely better find than a 55%/30% one.
That is the core of the system's appeal and it costs almost nothing to implement.

Resolution when a book is applied:

1. Roll `success`. On success the enchant is applied and the book is consumed.
2. On failure, roll `destroy`. On a destroy the **target item** is destroyed.
3. On failure without destroy, the book is consumed and nothing else happens.

Guard rails worth deciding on: whether a failed roll can destroy an item already
carrying enchants, and whether there is a level cap per item.

### Rarity tiers

| Tier | Colour | Success | Destroy | Feel |
|---|---|---|---|---|
| Common | white | 75–90% | 0–5% | safe to use on anything |
| Uncommon | green | 65–80% | 5–12% | mild risk |
| Rare | blue | 50–70% | 12–22% | think before using |
| Epic | purple | 35–55% | 22–35% | save it for good gear |
| Legendary | gold | 20–40% | 35–50% | genuinely a gamble |

### Consumables

All four are one item, `qfcontent:consumable`, as metadata 0–3, and all four are
used the way books are: pick one up, drop it on the thing it should affect.

| Item | Meta | Effect as built |
|---|---|---|
| **Magic Dust** | 0 | Drop on a **book**: +5% success, capped at 95% |
| **Ward Scroll** | 1 | Drop on a **book**: one shattering is absorbed |
| **Binding Scroll** | 2 | Drop on a **book**: success 100%, destroy 0% |
| **Solvent** | 3 | Drop on an **item**: dissolves one custom enchantment, chosen at random |

Ward Scroll is the important one — it turns Legendary books from "never worth
the risk" into "worth it once you've prepared", which is what makes a system like
this fun rather than punishing.

Three decisions worth recording:

- **The scrolls go on the book, not the item.** The design sketch had them applied
  to the target. Putting them on the book means the preparation is visible in the
  tooltip you are about to gamble with, and it means a prepared book is a tradeable
  object in its own right.
- **The ward is spent on the roll that would have cost the item**, not on
  application. A warded book that succeeds keeps nothing back, because it was
  consumed anyway — but the ward never burns on a roll that was safe regardless.
- **Solvent strips a random enchantment.** Letting the player pick would make it a
  way to walk a Legendary from one item onto a better one, one enchantment at a
  time, at no risk. Everything else in this system is a gamble; this is too.

Magic Dust is capped at 95% rather than 100% on purpose: guaranteeing an
application is the Binding Scroll's job, and it should stay the rarer answer.

## Build order

1. **Foundations** — DONE. Base class with the `canApply` override, ID
   allocation pinned to config, the dispatcher, six enchants covering every hook.
2. **Book + drag-and-drop together** — DONE. The book item with its NBT, the roll,
   and the `Container.slotClick` transformer.
3. **The full enchant list** — DONE. All 81, including the five that needed
   rendering or bytecode rather than an event handler.
4. **Consumables** — DONE. Dust and the three scrolls, applied the same way books
   are.
5. **Loot and quests** — DONE as far as code can take it: sealed tomes, the rarity
   pool, and vanilla chest generation. Actually placing tomes into BetterQuesting
   quests is authoring work in-game, not code.

Everything above compiles, registers and loads. What has *not* happened is a
playtest: whether the odds feel right, whether a Legendary is worth the risk, and
whether any given effect is fun are all questions the code cannot answer.

## Acquisition

The route is: **sealed tome → book → item.**

A sealed tome is one stackable item per rarity with no NBT. That shape is forced
by 1.7.10: chest generation copies a fixed template stack and BetterQuesting
rewards are stored stacks, so neither can roll a book's success/destroy chances at
the moment it is handed out. A book placed directly into either would be the same
book every time.

So the roll moves to the player's hand. A tome is safe to drop into any loot table
or quest reward, and opening one is an event rather than a silent inventory update.

- **Chest generation** — `EnchantLoot.registerChestLoot` adds tomes to dungeon,
  mineshaft, pyramid, stronghold and village-blacksmith chests, weighted
  12/8/4/2/1 from Common to Legendary. Consumables go in the same chests, dust
  common and the scrolls scarce.
- **BetterQuesting** — hand out `qfcontent:sealed_tome` with metadata 0–4 as the
  rarity. No integration code is needed; that is the point of the item.
- **Book level** is weighted toward 1, so a level 3 book stays a find.

The anvil route via `AnvilUpdateEvent` was considered as a stepping stone and
**dropped**: drag-and-drop is the real design, so building the anvil first would
have meant building something to throw away, and the drag-and-drop loop is
faster to test against for every enchant that follows.

### The ASM hook, for whoever reads this later

`ContainerTransformer` injects a call at the head of `Container.slotClick`.

It matches the method by **descriptor**, not by name:
`(IIILnet/minecraft/entity/player/EntityPlayer;)Lnet/minecraft/item/ItemStack;`
is unique within `Container`, so the same transformer works in a dev workspace
(MCP name `slotClick`) and in a real instance (SRG name `func_75144_a`) with no
name to get wrong. It logs which name it actually found.

Two things that will bite anyone editing it:

- **Stackmap frames.** The injection introduces a branch target, and Java 7+
  bytecode requires a frame there. `COMPUTE_MAXS` does not generate one, which
  produces `VerifyError: Expecting a stackmap frame at branch target 14`. The fix
  is an explicit `FrameNode(F_SAME)` at the label — the locals and stack there
  are identical to method entry. `COMPUTE_FRAMES` would also work but has to
  resolve common superclasses through the launch classloader, which is a much
  bigger hammer.
- **The hook must never throw.** `slotClick` handles *every* inventory click in
  the game, so an exception escaping the hook breaks all inventory interaction.
  `QFHooks.onSlotClick` catches `Throwable` and falls back to vanilla behaviour.
