# Dead items: what a player cannot get, and what has no use

Generated by `tools/items/dead_items.py` on 2026-10-25 from the 2026-10-17 item dump; the full table with every flag per item is `dead-items.json` beside this file. Written for the quest writers: what not to ask for, what not to hand out, and what the texture ranking can leave for last.

> **Read this first.** A "no known source" here means none of the data read by the script shows a way to get the item. The script does not read mob drops or dungeon loot coded inside mod jars, nor machine recipes outside the vanilla crafting registry, so the per-item research line ("how to get it") is quoted beside each verdict and is the better witness where the two disagree. "What the data cannot see" lists the blind spots.

## What the data cannot see

- Mob drops coded in mod jars (Lycanites, OreSpawn, TragicMC, Legends, Twilight Forest, HEE, Witchery ...): only what the descriptions say.
- Dungeon loot rolled in mod code (Roguelike Dungeons, Recurrent Complex, OreSpawn and TragicMC dungeons, Twilight Forest hollow hills and towers, Battle Towers): only ChestGenHooks tables and the pack's own loot configs were read.
- Machine, altar, cauldron and other non-vanilla recipes (Witchery, Railcraft rolling machine, ProjectE transmutation, Psychedelicraft, Legends Suit Assembly): only what the descriptions say.
- The 99 IRecipe objects whose getRecipeOutput() was null in the dump: the dump directory with their class names (unreadableTypes) is gone; only the count survives in recipes.json.
- MobProperties (224 mob files) adds no custom drops in this pack (every 'drops' list is empty), and Lycanites' custom-drop config lines are all blank; both were read, neither adds a source.
- Recipes a mod registers only once a world is open: the dump ran at the title screen, so Sync's core recipe (Sync.cfg hardcoreMode=2 decides it per world) is missing, and any other world-time registration with it.
- Mods the dump saw no crafting recipe for at all, although they have items: ChocolateQuest (its weapons and staffs are shop and dungeon loot by design), Recurrent Complex (creative tools), and Transformers, which is the suspicious one: its jar's TFRecipes class calls GameRegistry.addRecipe, addShapelessRecipe and addSmelting, so vanilla recipes exist in the mod, yet the dump holds none (its RecipeClearConfig class suggests a config can clear them, or they were registered after the dump ran). Its 44 'no-source' items are a dump gap to re-check in-game, not dead items.
- Mod jars were opened read-only for file listings only (Witchery's recipe class names, MCHeli's aircraft definitions); no class was decompiled.

**MCHeli.** 320 aircraft and vehicle definitions ship inside `MCHeli.zip`; the live client has an `assets/mcheli` folder beside `mods/`, and `bell47g.txt` is there, with `AddRecipe = " G ", "IXI", " I "` (glass, iron ingots, one iron block). The quest-book audit found that a dedicated trial server did not register `mcheli:bell47g`, and the play server at `C:\qfs\friends` has no `assets/mcheli` folder and no world yet to read a registry from. So the Bell 47G is craftable on the client and *unverified* on the server; quest 33 needs a server-side check (`/qfcensus` or the server world's `level.dat` registry) before it is called broken or fine.

**Loot config lines that never fire:**

- pack/config/Chocolate/ChestConfig/chests.prop: `potion= chocolateQuest:healingPotion 1,0,20` is malformed (a space where a comma should be), so this chest entry never rolls
- pack/config/Chocolate/ChestConfig/treasures.prop: `rustedSwordAndShield = chocolateQuest:rustedSword,1,0,1` names an item that does not exist (chocolateQuest:rustedSword), so this chest entry never rolls

## What to do with this

**A good quest ask is obtainable, visible and in tier.** Obtainable: status `ok` here, and ideally with a `recipe`, `chest-loot`, `worldgen-survey` or a description that names the mob or structure, so the item page tells the player how. Visible: it has a creative tab (no `no-tab`) and a real name (no `untranslated`), so it shows in NEI and the item browser; and it has an icon (`blank-icon` items render as a letter on the site and often as nothing in the quest book). In tier: the chapter order in `qb.py path` and the boss gates in `crazycraft_gating.zs` decide when a Twilight, OreSpawn or ProjectE item is reasonable to ask for.

- **Never ask for** anything in (a): `no-source`, `disabled`, `creative`, `technical`, `hidden`, or `quest-only`. Never ask for an MCHeli aircraft until the server check in (d) is done.
- **Candidates for a recipe or a loot entry** (then a quest): the (a) `no-source` rows whose research line is empty or says "no recipe" rather than "creative" or "technical": finished items the pack simply never hands out. Fix at the source (a CraftTweaker recipe in `pack/scripts`, a Lucky Block or loot-bag whitelist line) rather than by inflating quest rewards; balance changes wait for approval.
- **Candidates for a quest** (a reason to exist): the (b) rows with a real source and no use: trophies, props, coins, decorative items. A collection quest or a "show it" icon gives them a role without a recipe.
- **Candidates for removal or hiding**: the (a) `technical` and `hidden` families (placeholder block slots, crop stages, lit or burning variants, spawner blocks). They clutter NEI and the texture queue; the texture ranking can treat every id with a status other than `ok` as its tail.
- **Items whose only recipe is unreadable** (c): the quest text must explain the craft, since the item page cannot show it.
- **Rewards**: anything in (e) must go; `qb.py check ids` already blocks the three known cases. Items that are `quest-only` are fine to hand out but never to ask for.

To re-run: `py -3.10 -I tools/items/dead_items.py` after any change to the dump, the descriptions, the quest book or the loot configs; commit both outputs.
